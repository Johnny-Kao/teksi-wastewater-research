## A-01: prior claim corrected

Initial GC https://github.com/Johnny-Kao/teksi-wastewater-research/actions/runs/45061445286 tested the original upstream context-manager body but **incorrectly supplied autocommit=False**; its four passing tests are NOT evidence of a TEKSI production `__exit__` defect.

Real `plugin/teksi_wastewater/utils/database_utils.py` sets `DEFAULTS_CONN_ARG={"autocommit":True}` for psycopg3, and explicitly autocommit=True for psycopg2. Actual config GC https://github.com/Johnny-Kao/teksi-wastewater-research/actions/runs/45062218267: five PostgreSQL tests PASS:
- actual upstream config autosaves successful SQL before later Python errors
- a subsequent SQL error cannot undo a previously autocommitted statement
- changing only `__exit__` to rollback-on-exception cannot help
- explicit transaction contexts restore atomicity
- upstream context actually uses autocommit=True.

**Decision:** Do not propose `__exit__`-only patch; original A-01 issue is not established as a TEKSI defect. Any multi-statement atomicity change requires real producer contract and scope.

## A-02a: trigger-cleanup control-flow gap

The original `InterlisImporterExporter.interlis_import` performs:
`self._import_disable_symbology_and_modification_triggers()` immediately **before** its exception-cleanup `try` block. The helper runs the two disable operations sequentially. Both use autocommitted PostgreSQL SQL.

A fault-injected test dynamically compiles the exact upstream methods, executes PostgreSQL state changes, and injects a failure into the second disable. GC https://github.com/Johnny-Kao/teksi-wastewater-research/actions/runs/45062369442 PASS 2/2:
- second disable fails -> first remains disabled, exception bypasses cleanup.
- failure inside the later `try` -> both trigger groups are restored.

**Limits:** Synthetic dependency, a reduced PostgreSQL flag table (NOT a deployed TEKSI database, QGIS, or real trigger DDL). Real-world database/permission/network fault incidence unknown. The SQL implementation of symbology/modification triggers uses ALTER TABLE ... DISABLE TRIGGER, hence a persistent database-level state, not only Python memory. With a clean second-statement failure, only symbology triggers remain disabled; distinguish their impact from modification triggers. Existing historical issue #485 demonstrates damaging consequence of disabling modification triggers during deletes, but does NOT prove this new fault path occurs in the field.

## A-02b: post-commit integrity-check ordering

Main INTERLIS import session commits **before** sequence reset, main-cover/node update, materialized-view refresh, subclass-integrity check and organization activation. Any postcommit failure cannot roll back already-committed import data; a manual retry or cleanup may be necessary. However this ordering may be intentional, and neither corrupted real TEKSI data nor failed retry has been demonstrated. Historical user report #609 mentions subclass-count warnings after successful import; not evidence of the exact current failure mode.
